# Offline live-translation regression fixtures

Run from `backend` with the project's Python environment:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

These tests do not call Gemini and do not need `GEMINI_API_KEY`.

## Audio fixtures

- `fixtures/audio/speech_pause_speech.wav` is deterministic synthetic harmonic audio with two voiced-like blocks and a labeled 600 ms digital-silence interval. It checks PCM format, frame size, and later VAD boundary logic. It is **not human speech** and must not be used to evaluate speech recognition or translation quality.
- `fixtures/audio/silence_100ms.wav` is exactly one 100 ms PCM16 frame of silence.
- `fixtures/audio/generate_audio_fixtures.py` regenerates both WAV files.

The live websocket uses `PauseDetector`, a simple RMS energy endpoint detector. Defaults are `LIVE_VAD_RMS_THRESHOLD=450` (PCM16 RMS units), `LIVE_VAD_MIN_SPEECH_MS=200`, and `LIVE_VAD_SILENCE_MS=600`; all can be overridden in `.env`. The default `provider_activity_mode=manual` disables provider VAD and sends `activity_start` / `activity_end` around locally detected utterances. An experimental `automatic` mode streams all frames to provider VAD; `hybrid` additionally sends `audio_stream_end` at local pauses. The manual mode keeps a short pre-roll while confirming speech. Since Live Translate may stream continuously without turn-completion or transcript-finished markers, local VAD pauses are candidate segment boundaries, not sentence boundaries by themselves. Before automatic save, source and translation must both end with terminal punctuation and the translation must not have fewer sentence-ending marks than the source. The backend then waits for a quiet transcript window (`LIVE_SEGMENT_SETTLE_MS`, default 2500 ms). Pauses inside a clause or sentence stay pending and may be coalesced with the next pause. WebSocket partials remain immediate; the longer wait only affects persistence. This is a tunable heuristic, not a noise-robust neural VAD, and real audio regression tests are needed to measure late-fragment misassignment.

## Event fixtures

`fixtures/live_event_sequences.synthetic.json` contains hand-authored normalized mock scenarios: chunked transcripts over multiple turns, a provisional transcript corrected by a final transcript, stopping before translation arrives, and reconnecting to a new provider stream while keeping the same database session.

These are test scenarios, **not captured Gemini SDK messages**. The fixture keeps that distinction explicit so it cannot be mistaken for evidence of actual model behavior. Later, real provider recordings can be added after the event contract and privacy-safe capture policy are defined.

The transcript tests exercise `TranscriptAssembler`: provisional input is treated as a replaceable preview, finalized fragments are appended without fuzzy overlap deletion, and buffers reset between turns. Long cumulative input updates replace their shorter prefix; stale cumulative updates are ignored. A shorter canonical event without an explicit `finished` marker no longer erases a longer cumulative interim tail; automatic segment finalization waits for that tail to resolve. At forced stop, a longer cumulative preview can supersede a shorter canonical prefix and the full source is retranslated when needed. The browser merges cumulative display snapshots with committed text to avoid showing the same prefix twice. A conservative four-token prefix check avoids treating short repeated phrases as snapshots; the status line reports how often cumulative replacements and stale updates occur. `VADBoundaryTracker` requires both transcript sides to have sentence-ending punctuation and a quiet settle window, and holds a candidate boundary while speech is active. A provider completion marker no longer commits immediately: it wakes the boundary tracker, which still waits for a local pause and a quiet transcript window before saving. Stop forces a final flush after audio and transcript draining. Real Gemini event timing still needs a microphone test because provider event ordering, delivery delay, and optional timing fields can vary by model/API version.


Persistence checks both sides before reporting success. A missing translation or an unrepaired live translation with fewer sentence endings than the source is retained as `failed` for retry. At an explicit clean Stop, any source without terminal punctuation is saved as `fragment`, with whatever streamed target text exists marked provisional; a provider or audio drain error or timeout still yields `failed`. This conservative rule prevents a plausible but unfinished phrase such as `Cảm ơn bạn vì đã đến tham dự` from being marked `completed` before the next words arrive. The legacy `source_confirmed_without_punctuation` / `stop_source_confirmations` event fields remain for compatibility but are not activated by the current automatic Stop policy. A successful non-streaming translation of the entire source may combine source sentences, so different punctuation counts are allowed. These checks are not a semantic proof that the translation is complete; verify real provider output and inspect false successes/failures. A durable pending segment ID is loaded from SQLite on reconnect. Saving a segment and advancing to its deterministic successor happen in the same transaction; replaying the same persistence request with identical contents returns the existing row, while reusing the ID for different contents is rejected. This prevents duplicate database rows from a retried finalization. It does not deduplicate audio bytes replayed by a client because the current binary frame contract has no frame IDs.

A standalone request prefix (`Xin` in Vietnamese, `Please` in English) is intentionally classified as incomplete, including when ASR adds terminal punctuation. After a clean explicit Stop it remains in `source_text` with status `fragment`; any target-language text is kept as a provisional preview and may be wrong. Fragments count toward ordered transcript/summary input and do not block finish. Summary aggregate strings exclude provisional targets. On reconnect to the same session and direction, `continue_fragment=true` (default) joins new source speech to the final fragment and retranslates the whole phrase; `false` starts a new segment. The revision uses the same segment ID and sequence number. Provider failures remain `failed` and retryable. `Xin chào bạn.` remains complete; genuine repeated speech is preserved. This is a narrow lexical rule, not a general grammar or semantic completeness classifier.

## Stop and reconnect behavior

On Stop, the backend appends the final pending PCM frames and a manual `activity_end` marker in manual mode; automatic/hybrid modes send `audio_stream_end` when there is unsent audio. It then uses one FIFO stop marker in the bounded queue. It does not discard queued frames to make room for the stop marker. Queue draining has a 20-second limit (`LIVE_AUDIO_QUEUE_DRAIN_TIMEOUT_MS`); sender draining and provider transcript draining also have bounded waits. After the sender has delivered the final audio, late transcript activity restarts a quiet window (`LIVE_STOP_QUIET_MS`, default 2500 ms), capped by `LIVE_STOP_DRAIN_TIMEOUT_MS` (default 20 seconds). The browser waits up to 90 seconds before treating Stop as unresponsive.

If the final source transcript has terminal punctuation but the streamed translation is missing it or has fewer sentence endings than the source, the backend makes one bounded text-translation repair attempt. The successful text repair is based on the whole source, so it may combine sentences; it is accepted when source and repaired translation both end with sentence punctuation. If the source lacks terminal punctuation at a clean Stop, it remains `fragment` for possible continuation. If repair fails for a punctuated source, the source and any partial translation are retained as `failed` for retry. Sentence-count comparison is a guard for streamed output, not a semantic completeness proof.

Starting the live page again reloads the persisted session transcript before requesting microphone access. This restores the app's visible history. The backend also stores the latest provider resumption handle per session/model/target language and attempts Live API session resumption on reconnect. The provider may reject the handle; if so, the backend clears it and safely opens a fresh stream, reporting `context_restored=false`. The selected Live Translate model's compatibility with resumption still needs a real provider test. Prior transcript text is not injected into the model because the Live Translate guide documents audio-only input and says text input is unsupported. The session connection guard is process-local; a multi-worker deployment needs a shared lock/lease service.

## Latency and multi-session handoff

`GET /api/v1/metrics/live-latency` reports sample count, p50, p95, and maximum for audio-to-source, audio-to-translation, Stop-to-final-persistence, and provider connection setup. Provider connection samples are also grouped by `fresh`, `resumed`, and `resume_fallback`. These values are meaningful only after real microphone sessions have recorded samples; the synthetic WAV fixtures are not speech-recognition or translation benchmarks.

`GET /api/v1/sessions/{session_id}/live-diagnostics` returns the latest stopped connection's bounded event timeline. It records local VAD starts/pauses, provider activity markers, provider transcription chunks and attempts to send partials to the browser; it excludes raw audio and stores only the last 80 text characters per event. Use it to distinguish a word withheld by Gemini from one delayed after backend receipt. An offline WebSocket test verifies event order and persistence; real microphone timing still requires a live run.

For a presentation composed of several sessions, finish each session with `POST /api/v1/sessions/{session_id}/finish`, then finish the presentation with `POST /api/v1/presentations/{presentation_id}/finish`. `GET /api/v1/presentations/{presentation_id}/summary-input` returns the ordered bilingual transcript grouped by session for the T5 teammate. The backend assembles input and does not run T5.

The retry regression tests use a real temporary SQLite row in status `failed`, but mock Gemini's response and outage. They verify the database state transitions and retryability; they do not prove an actual Gemini retry request. The offline suite uses no API key and does not contact Google.
